# 地铁巡检仿真与平台双周工作汇报

- 本阶段主线：更新隧道与 V6 巡检车，打通传感器、运动、病害定位和五相机巡检平台

## 一、阶段目标

本阶段的目标是把前期分散在旧仿真工程、硬件分支和队友 mapping 分支中的成果，整理到统一的 `metro-inspection` 工程中，并形成一套可以继续接入真实 YOLO 的仿真基础。重点包括：

1. 使用最新隧道和 V6 小车替换旧模型，并完成轮轨尺寸适配。
2. 让车辆依靠车轮转动和轮轨接触运动，不再使用直接修改位姿的滑动方式。
4. 接入队友的图像与点云融合代码，验证二维检测结果转换为三维坐标的链路。
5. 建立能够显示五路相机和真实病害事件的巡检平台。

## 三、主要完成内容

### 3.1 项目结构与模型管理

- 将稳定仿真成果迁移到 `metro-inspection`，机器人描述集中在 `metro_description`，Gazebo 运行模型集中在 `metro_sim/models`。
- 明确 URDF 与 Gazebo Model 的职责：URDF 负责机器人结构、关节、TF 和传感器描述，SDF 负责 Gazebo 实际运行模型。
- 清理旧 `gazebo_train_tf.urdf`、过期拆分网格、重复贴图说明和 Windows `Zone.Identifier` 文件。
- 为 184,021,697 字节的隧道 DAE 启用 Git LFS，避免大模型直接进入普通 Git 对象历史。
- 将模型导入和 SDF 生成设计为“替换”操作而不是“追加”操作，避免反复执行后出现重复模型和冗余网格。

主要目录：

```text
ros_ws/src/metro_description/     机器人 URDF、源网格和导入脚本
ros_ws/src/metro_sim/models/      Gazebo 运行模型
ros_ws/src/metro_sim/worlds/      预览、传感器、建图和融合世界
ros_ws/src/metro_mapping/         图像-点云融合与三维定位
ros_ws/src/metro_dashboard_bridge/ ROS 2 与网页平台桥接
dashboard/                        五相机巡检页面
```

### 3.2 图像、点云与病害三维定位

- 从队友 mapping 分支整理并接入 `metro_localization` 与 `metro_closed_loop` 两个 ROS 2 包。
- 当前验证的数据链为：

```text
/odin1/rgb/image_raw
/odin1/rgb/camera_info
/odin1/cloud_raw
/damage_detections
/tf 和 /tf_static
  -> 图像/点云时间同步
  -> 点云投影到图像
  -> 检测框或掩码内点云筛选
  -> DBSCAN/中值估计
  -> /damage_point_camera
  -> TF 转换
  -> /damage_point_global
```

- 增加投影调试图、三维位置 Marker、误差评估和隧道里程/区段/时钟方位语义计算代码。
- 红色 HSV 检测器仅用于验证消息链路，会把红色轨道部件误识别成病害，现已默认关闭。
- 真实检测节点需要发布 `vision_msgs/msg/Detection2DArray` 到 `/damage_detections`。
- 队友演示世界中的预设真值坐标和里程常数不属于当前隧道，因此评估器和语义映射器默认关闭，待重新标定后启用。

### 3.3 五相机巡检平台

- 新增 `metro_inspection_interfaces/msg/DefectEvent`，统一承载二维检测框、三维坐标、定位方法、置信度、里程、区段和隧道方位。
- 新增 `metro_dashboard_bridge`，订阅五路压缩相机图像和 `/defect_events`，向网页提供只读 API 与 MJPEG 流。
- 平台现有能力：
  - 桌面端同时查看 XJ1～XJ4 和 Pitch 五路实时画面；
  - 移动端只连接当前选择的一路，降低传输和解码压力；
  - 显示相机在线状态、源帧率和最新帧时间；
  - 按相机、病害等级筛选记录；
  - 展示二维框、三维位置和隧道语义；
  - 生成等级/类型统计和可打印巡检报告。
- 页面不生成随机病害，只有 ROS 2 收到真实 `DefectEvent` 后才显示记录。
- 相机预览默认限制为最大 `640 x 360`、JPEG 质量 55、每路 6 FPS；三秒没有新帧时显示离线。
- 平台与完整传感器仿真统一使用 `ROS_DOMAIN_ID=70`，解决仿真话题存在但网页无法发现的问题。

## 五、当前边界与风险

1. 当前没有接入真实 YOLO，系统已具备输入接口和三维定位能力，但不能把 HSV 测试结果当作真实病害识别结果。
2. 五路巡检相机尚缺每台设备独立标定参数，现有参数复用只适合仿真联调，不能直接代表最终测量精度。
3. `odom` 会随轮滑和累计误差漂移；长距离三维建图和病害绝对坐标仍需要激光里程计、SLAM 或融合定位提供稳定的 `map -> odom`。
4. 当前里程、环号和标准答案参数来自队友演示配置，未针对 `tunnel_8.10` 建立正式基准，因此默认关闭。
5. 完整六相机、高分辨率 Odin1 和 Gazebo GUI 同时运行时计算负载较高，正式演示应按任务选择 Sensors、Mapping 或 Fusion 模式。
6. 平台病害记录当前保存在进程内存中，服务重启后会清空，后续需要数据库和截图存储。
7. 云台 Yaw/Pitch 当前锁定在 CAD 零位；若需要动态巡检角度，需要补充控制器、限位和初始位置管理。
